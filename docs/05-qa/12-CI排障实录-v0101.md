# CI 排障实录：v0.10.1 双 bug（编译层 + 测试层）+ 签名缺失根因

> 目的：完整记录 2026-08-15 排查「cargo test --lib 在 ubuntu CI 失败、本地 Windows 全绿」的整个过程——根因、证据链、修复、方法论。未来遇到「本地过、CI 挂」直接对照本实录，不要重复踩坑。

## 1. 现象

- Release / CI workflow 的 **Rust tests step** 失败（exit 101），从 a39f6ce（multi-AI backend）合入起连续多次 run 全失败
- 本地 Windows `cargo test --lib` **230/230 通过**（含 3 个 #[ignore] 真实环境测试）
- 日志网页因网络受限不可读，只能靠 API 间歇窗口

## 2. 根因（两个独立 bug 叠加）

### Bug ①：ubuntu 缺 libssl-dev → openssl-sys 编译失败

- `reqwest`（features=["json"]）默认 **native-tls → openssl-sys**；Linux 编译 openssl-sys 需要系统 `libssl-dev + pkg-config`
- **Windows 用 schannel（系统自带），无需任何库** → 本地永远编译通过
- CI 的 apt 安装列表（ci.yml / release.yml）从未包含 libssl-dev
- 平时被 **Rust cache**（`Cargo.lock` hash 命中）掩盖；cache 过期/miss 时全量编译 → 暴露
- 证据：失败日志尾部 = `Compiling openssl-sys` 等编译进度 + exit 101（无任何测试输出）
- 修复：三处 apt 步骤加 `libssl-dev pkg-config`（commit 6bb64f1）

### Bug ②：sidecar 测试断言 Windows 专属行为 → unix 分支 panic

- `commands::tests::sidecar_command_targets_the_script`（src-tauri/src/commands/mod.rs）断言 `args.len() == 1`
- Windows 分支 `sidecar_command` = `python <script>`（1 个参数）✅；**unix 分支直接执行脚本（args 为空）→ panic at mod.rs:88**
- 该测试由 5034ab3 引入，作者只在 Windows 上验证过
- 修复：改为跨平台断言（program + args 任一包含脚本名，commit 6a2dc26）

### Bug ③（发布层，排障中顺带发现）：签名从未生效

- `tauri.conf.json` 的 `bundle` 区块**缺少 `"createUpdaterArtifacts": true`**（tauri v2 字段，v1 的 `bundle.updater.active` 在 v2 不存在）→ tauri v2 **不生成任何 .sig 文件**
- 结果：所有版本（v0.8.1 起）release 资产无 .sig，`latest.json` 的 signature 为空（9 字符）→ **自动更新签名验证一直失败**
- GitHub Secrets（TAURI_SIGNING_PRIVATE_KEY / PASSWORD，2026-07-04 配置）**从未被使用过**
- 修复：`bundle.createUpdaterArtifacts = true`（tauri-build 配置校验通过；曾误写 `bundle.updater.active` 触发 unknown field 编译错误）

## 3. 证据链（网络受限下的排障方法论）

| 步骤 | 手段 | 结论 |
|---|---|---|
| 1 | API 间歇窗口拿 run/jobs 列表 | 失败点 = Tests job 的 Rust tests step；verify/frontend 通过 |
| 2 | jobs API 的 step 级详情 | Rust tests step 122 秒 → 正常时长，非挂起 |
| 3 | 本地全量复现（cargo test / vitest / tsc / npm ci dry-run / 死端口 Ollama 模拟 / 2 线程模拟） | 全部通过 → 平台差异 |
| 4 | 静态分析 a39f6ce 引入内容 | 纯解析测试 + 重构，排除 |
| 5 | **annotation 通道**（workflow 加 `tee` + `::error::` 输出日志尾部） | 首次拿到真实日志：`Compiling openssl-sys` + exit 101 → **编译失败** |
| 6 | 迭代修复诊断（%0A 转义 → grep 过滤错误行） | 最终拿到 `sidecar_command_targets_the_script ... FAILED` + panic 位置 |
| 7 | 修复后直连 API 确认全绿 | 双 bug 确认修复 |

**关键方法论**：
1. **日志网页不可读时，把失败详情写进 check-run annotation**（`::error title=...::`，注意换行必须转义 `%0A`，且用 `grep` 过滤 error 行——cargo 编译进度会淹没日志尾部）
2. **本地全绿 ≠ CI 绿**：优先怀疑平台差异（TLS 后端、命令行为、路径、环境变量）
3. **cache 会掩盖编译依赖问题**：cache miss 才能暴露
4. **gh-proxy 的 API 限流是共享账号池**（403 响应里的 user ID 会变化），直连可用时优先直连

## 4. 防复发（已落地）

- ci.yml / release.yml：apt 加 `libssl-dev pkg-config`
- ci.yml / release.yml：Rust tests 失败自动输出 annotation（保留为排障基础设施）
- release.yml：updater-json job 加签名空检查（.sig 缺失 → error + exit 1，阻断发布）
- AGENTS.md：新增「CI / 发布速查」区块（本实录的浓缩版）
- docs/04-deploy/发布流程.md：§6.3 补 bundle.updater.active 配置；检查清单加 .sig / latest.json 签名验证
- tauri.conf.json：bundle.updater.active = true
