## 二、可用性 99.9% 的工程口径

桌面应用没有服务端 SLA，把 99.9% 写成「服务在线率」是空话。本项目的可证伪口径：

1. **会话成功率**：localStorage 的 sessions 为分母、crashSessions 为分子（同一会话多次异常只计一次）。
2. **命令级可用性**：读命令 3 次指数退避重试（src/lib/tauri.ts），写命令不重试；失败必然对用户可见（F-3 已修）。
3. **降级可用**：AI 后端不可用时，图库/搜索/标签/回收站/导出等本地能力不受影响（check_ollama_status 3s 超时，只影响 AI 面板）。
4. **不再挂死**：所有 sidecar 调用统一走 run_with_timeout（默认 600s，超时杀整棵进程树），CPU 密集任务移出 async 执行器。

## 四、性能基准装置

### 页面加载（TC-PERF-001，已实测通过）

生产构建（npm run build:perf + vite preview）实测：

```text
TC-PERF-001 load metrics: {"domContentLoadedMs":35.1,"loadEventMs":35.3,"fcpMs":48,"appShellMs":98.6,"resourceCount":33}
TC-PERF-001 first interaction: 417 ms
TC-PERF-002 scroll baseline: {"frames":424,"avgMs":7.09,"p95Ms":8.7,"fps":114.9}
```

- 口径：navigationStart → 应用外壳挂载且可交互（首屏真实可用，不是骨架屏）；断言读页面内的 Navigation Timing / Paint Timing，而不是测试框架墙钟。
- **必须跑生产构建**：dev server 按需转译模块，同一页面在 dev 下测得 DCL 3.4s / FCP 2.2s，那是转译开销而不是应用性能。playwright.config.ts 因此拆成 core（dev server，2 workers）与 perf（生产构建，1 worker 串行）两个 project：早期混跑时，6 个并发页面把 dev server 打满，测出来的「加载时间」全是资源争用。
- 品牌启动动画是叠加在已加载应用之上的幕布，按决策压缩为 900ms 保持 + 240ms 淡出；用例内含「动画预算 + 外壳预算 < 2s」常量断言，防止将来被悄悄加长。

### API P95（src-tauri/src/perf_bench.rs，10k 图库）

覆盖 9 个用户可感知读路径；每场景 1 轮预热 + 60 轮取样，任一场景 p95 ≥300ms 即断言失败。下表为 **2026-09-17 空载运行**（Windows 11 / MSVC / 10k 图库）：

```text
scenario                                     p50(ms)   p95(ms)   p99(ms)   max(ms)
list_images(page 1, 40/page)                    6.79      8.37     10.74     10.74   OK
list_images(page 100, 40/page)                 30.16     43.43     45.55     45.55   OK
list_images_filtered(favorite+min4)             6.17      6.55      6.98      6.98   OK
list_images_filtered(model=sdxl)               42.79     45.18     47.03     47.03   OK
search_images(fts: neon rain)                  37.92     39.27     40.69     40.69   OK
search_images(fts: single rare token)           0.74      1.07      1.21      1.21   OK
search_images(fts: operator-only)               0.00      0.00      0.00      0.00   OK
get_dashboard_stats                            50.12     53.95     54.96     54.96   OK
get_images_by_ids(40, same page)                4.67      5.13      5.33      5.33   OK
list_tags                                       0.03      0.09      0.19      0.19   OK
worst P95: 53.95 ms (budget 300 ms)
```

**波动说明**：同一套用例三次实测最差 p95 = 60.69 / 132.97 / 53.95 ms —— 差异来自机器负载（第二次是与测试套件并行时跑的），不是代码变化。三者的结论一致：都在 300ms 预算内。这个基准测的是**机器相对表现**，只有显著超出预算才代表回归；引用时应说明当次负载状况，而不是挑一个最好看的数。

读法：SQLite 层最慢的是深分页与全库聚合（`page 100` 的 OFFSET 3960、`get_dashboard_stats` 的多次 COUNT），都在 70ms 内；纯操作符查询走空守卫直接返回，因此是 0ms。这条路径的口径是 **DB 层 + 真实行/标签解码**，不含 IPC——IPC 序列化在页面加载 E2E 里已由端到端时延覆盖。

#### 测量环境纪律（本轮踩坑记录）

这两个 E2E 性能门禁对**机器负载和残留进程**极其敏感，一次误判就足以让人怀疑应用：

| 现象 | 真因 | 处置 |
|---|---|---|
| DCL 从 47ms 跳到 **5017ms** | 累计 64 个孤儿 msedge/msedgewebview2 进程（历次失败运行残留） | 清理后立刻恢复 39ms；用例已加「DCL > 1s 视为环境污染，重测一次并打印两次读数」，**预算仍在重测上强制执行**，真回归藏不住 |
| 页面加载 E2E 报 2s 超时 | 与 `vitest` **并行**运行，两者抢 CPU | 串行执行；vitest 的 jsdom 环境本身开销就大 |

因此在 CI 上这两个 project 是独立的 job、不与其他重型任务并行；本地跑之前建议先 `Get-Process msedge,msedgewebview2 | Stop-Process -Force`。

```bash
cd src-tauri && cargo test --lib perf_bench -- --ignored --nocapture
```

## 五、灾难恢复（RTO/RPO）

- **RPO**：auto_backup::INTERVAL = 10min（< 15min 预算），启动即拍第一份、保留最新 6 份并清理旧快照；快照走 SQLite Online Backup API，因此 WAL 中「已提交未 checkpoint」的数据不会丢（有用例专门断言该场景）。
- **RTO**：恢复 = 快照走既有 import_database 路径（活动连接内 backup API，不换文件、不残留旧 WAL）+ PRAGMA integrity_check。
- **演练**：rto_drill_restores_full_library（Rust 用例：全损 → 恢复 → 完整性校验）、scripts/restore-drill.mjs（终端演练与报告）。

## 七、结论（2026-09-18 复测）

- **本机实测已达标（9 项中 7 项，今日全部重跑确认）**：
  - 页面加载 <2s —— 生产构建外壳 **151.8ms**、首次交互 **418ms**（TC-PERF-001 2/2 通过）
  - API P95 <300ms —— 最差 **132.97ms**（并行负载下，仍远低于 300ms）
  - 核心覆盖率 ≥80% —— 前端 **87.79%** 行、Rust **81.44%** 行 / **80.22%** 区域
  - 高危漏洞 = 0 —— npm **high=0 critical=0**（moderate=3 仅测试工具链）
  - RTO <4h —— DR-01 演练墙钟 **4.34s**，恢复耗时可忽略
  - RPO <15min —— 自动快照 **10 分钟**间隔 + 6 份保留（含 WAL 未 checkpoint 场景用例）
  - P0/P1 缺陷 = 0 —— 前端 **972**、Rust **285** 用例全通过；`cargo fmt --check` 与 `cargo clippy -D warnings` 通过
- **装置就绪、需长周期样本才能声称达标（2 项）**：可用性 99.9%、崩溃率 <0.1%。两者都依赖真实使用累积的会话/异常计数（设置→数据备份→稳定性 可直接读数），**不接受用一次跑分代替**。
- **工程门禁在 CI 持续拦截**：覆盖率阈值写入 vitest.config.ts / cargo llvm-cov --fail-under-*；npm high/critical 与 cargo audit 在 security-audit.yml；页面加载在 E2E perf project；P95 在 `perf_bench`（--ignored 显式跑）。
- **历史自查（2026-09-17）**：新写的 4 个 Rust 测试首次真机运行全部失败（panic 计数竞态、OnceLock 目录竞态、百分位样本量算错等）——「编译通过 ≠ 测试通过」。现已全部修正，2026-09-18 复测 285 用例真机全绿。
